量衡 EvalLab · AI 效果评测体系
独立产品 · 问题定义 / 评测体系设计 / 数据分析 · 2026.09
以下为完整项目内容
4 类评测任务
806 条全量回归数据
+1.59抓出的自偏好偏差
13.0%→0%未归类率

工作台里有 5 条 AI 链路在调 LLM，但「选哪个模型」一直靠手感——直到我把它做成一个能回答的问题。做法：真实业务数据造金标 → 规则 + LLM-as-judge 双层指标 → 双 judge 盲评交叉 → 质量 × 成本 × 延迟三维榜单。最后交付的不是一张表，是三个能直接执行的决策。

评测怎么设计 · 4 层结构，每层都在防一种失真

第 1 层
真实业务金标
不用公开榜单当评测集。81 条时间轴分类金标从 180 条候选里人工清洗，8 段工作日志、30 条随想回应全部来自生产快照——防「考的不是我在做的事」。
第 2 层
双层指标
确定性任务用规则（准确率 / macro-F1 / 混淆矩阵），主观任务用 LLM-as-judge rubric（4 维 × 5 分制）——防「拿一个分数糊弄所有任务」。
第 3 层
双 judge 盲评交叉
两个模型互评，再抽 20% 隔轮重评一遍，用来量「裁判自己可不可信」——防「裁判偏心却没人知道」。
第 4 层
三维榜单
质量 × 成本 × 延迟同轴呈现，成本按牌价算、延迟记 P50 / P95——防「只比质量，选出一个上不了线的模型」。

4 个真实结论 · 每一张图都是一个决策依据

① 公开榜单分不出胜负，业务数据一秒见高下核心洞察
同一个模型对，在公开基准 ChnSentiCorp（120 条）上只差 0.8pp（82.5% vs 81.7%）；换到自家业务任务上差距立刻拉开——工作日志硬约束差 37.5pp（100% vs 62.5%）。设计判断：通用榜单衡量的是「谁更像人」，我在意的是「谁在我的场景里不出错」，这两件事不是一回事。
② 我自己审我自己的评测，抓出裁判偏袒评测的评测
让模型当裁判，它会给自己打高分：deepseek-chat 评自己均分 4.50、评对手只有 2.91，Δ = +1.59。同一批 100 条样本、同一份 rubric，差别只在「谁在打分」。处理：改用剔除自评的交叉口径对外报分——设计判断：指标不先自证可信，结论就没有意义。
③ 806 条生产数据全量回归，才敢说「可以换」决策验证
时间轴分类原本用关键词典，105 条（13.0%）落不进任何类目。用横评胜出模型全量重跑 806 条：未归类 105 → 0 条，与词典判断一致 573 条（71.1%），全集成本 ¥0.50、0 次调用失败。设计判断：抽样说好不算数，全量回归过了才算——分歧点还专门做了人工复核归因。
④ 又准又便宜的那个，才是能上线的那个三维榜单
GLM 免费档便宜到 ¥0，但准确率低 12.4pp、P50 延迟高 65%（1203ms vs 730ms）。设计判断：「免费」本身不是选型依据，「在质量红线上还免费」才是——所以 GLM 保留为兜底档，不占主链路。

可信度审计 · 这些数字凭什么可信（也写在局限里）

  • 双 judge 一致率：分差 ≤1 口径下 6 个维度分别为 76.5% – 99%（最低 persona_fit 76.5%，最高 concise 99%）。
  • Cohen’s κ 偏低（0.05 – 0.38）—— 如实说明：主观维度分数高度集中，κ 对低方差本来就苛刻。所以全部结论只作相对排序，不当作绝对质量分。
  • 隔轮重评漂移：B 任务 0.125 分（n=16）、C 任务 0.054 分（n=424），judge 打分本身是稳定的。
  • 未做的三件事（不粉饰）：judge 与被评模型同源、第三方 judge 未接入、样本量仍是试点规模、成本按牌价计、延迟未测首字。

结论 · 三个直接可执行的决策

  • ① 模型路由：质量敏感链路主模型锁 deepseek-chat，GLM 免费档只做兜底——依据是 B 任务 37.5pp 的硬约束差距，不是价格。
  • ② 产品迁移：时间轴分类从关键词典迁 LLM，已完成 806 条全量验证（未归类 13.0% → 0%，成本 ¥0.50），迁移动作按此排期。
  • ③ 质量红线：立下三条不可越线指标——A 任务准确率 ≥85%、B 任务规则通过率 100%、C 任务 rubric ≥4.0。以后换模型 / 改 prompt，先过回归再上线。

方法论对标 · 不是从零想的

  • promptfoo（声明式配置）→ 借鉴其「评测即配置」的组织方式，但不引入框架依赖。
  • deepeval（指标分层）→ 借鉴确定性指标 / 主观指标的分离，落成我的双层指标。
  • ragas（用生产数据建评测集）→ 这是「不用公开榜单当评测集」这条设计的直接来源。
  • OpenCompass（榜单呈现）→ 借鉴其多维同轴的表达方式，把质量 / 成本 / 延迟放在一张榜上。

一个把「自我调试」做成产品的系统：记录 → 抽离 → 定位 → 修复 → 迭代。产品直觉不是假设出来的，是从 1500+ 条真实行为记录里长出来的。核心方法论：面对 AI，要有自己的判断——所以我给内容管线加了 4 道过滤。

核心方法论 · 4 道内容过滤闸门

闸门 1
素材黑名单
剔除 AI 合成类素材源，不让 AI 喂养 AI。
闸门 2
水位线 T
只消化上一周期之后的新内容，不重复捕获陈旧信息。
闸门 3
信息四分类
强制分类：事实 / 数据 / 观点 / 推断，置信度透明。
闸门 4
dry-run 演习
推送前用历史周跑一遍验证稳定性，发现退化立即停推。

4 个亮点场景 · 不拼功能数量，每一张都在讲产品判断

① 全貌 · 19 模块在一个 SPA产品入口
左侧导航 + 主区切换，本地 IndexedDB + 云端多端同步。设计判断：19 个模块不是想到一个加一个，是按「我怎么理解生活」切出来的——分组本身就是个产品决策。
② 时间轴 · 粘贴即落库每日最常用
一行文本直接落到对应小时，无表单无选择器。设计判断：记录摩擦越低越好，不该让工具本身成为负担。
③ AI 日报 · 自动推送 + 成本可控每日 20:05
token 用量实时监控 + 模型降级链（3 级 fallback）。设计判断：LLM 不能黑盒跑，必须有 token 预算 + 模型切换 + 失败告警。
④ 认知吸收卡 · 4 道闸门的实际生效处核心差异化
GitHub 周榜 → AI 消化 → 认知吸收卡。前面 4 道闸门就是这个卡片的实际生效位置——不是嘴上的方法论，是跑通了 13 周的机制。

三个视图 · 一份档案 · 产品判断藏在默认值里

① 今日帖 · 该投的 / 该催的 / 该备战的每日首页
打开第一屏只回答一个问题：「今天该干什么」。每条带行动按钮（投了 / 催一下 / 去备战），右侧投递总览 + 近 7 天新增。设计判断：追踪器的价值不是记录全，是「此刻该做什么」够明确。
② 牌阵 · 六态流转 + 拖拽推进核心交互
想投 → 已投 → 笔试 → 面试 → 已转生 → 落樱。拖一张牌到下一列即推进，自动写历史记录；流程 / 公司 / 月历三种视角切换，社招用户可一键切成无笔试列的精简流程。点开一张牌即翻档案：公司 / 岗位 / 城市 / 渠道 / 薪资 / 简历版本 / 届别核验 / 适配度 / 下一步动作，DDL 倒计时超时自动标「需跟进」。设计判断：求职本身够焦虑了，界面要做的是把它变成「可摆弄的牌」。
③ 试炼 · 面试复盘长成题库闭环设计
每轮面试记下「被问倒的题」，自动汇成按公司筛选的刷题库（内置 22 道通用种子题）。三处 AI 接手：答题思路（破题 → 作答框架 → 亮点收尾）、面经收题（贴面经原文抽真题，明令禁止编题）、盘下一轮（读完复盘点名薄弱点）。资讯侧由服务端每天定时采集对口面经，前端只管看。设计判断：失败也要变成资产，复盘不是写完就死的笔记。
④ 三视图一屏看 · 单文件能扛多少工程取舍
今日帖 / 牌阵 / 试炼三个视图、六态状态机、月历与法定节假日标注，全部装进一个 HTML 文件：0 构建、0 依赖、离线双击可用，GitHub Pages 直接发布。设计判断：工具不能比它解决的问题还重。

设计过程 · 从需求定义到视觉定稿

  • 需求定义一页纸：先写清问题、用户、边界与「不做什么」，再动手——避免边做边漂移。
  • 信息架构页面地图：今日帖 / 牌阵 / 试炼三页职责划分，页面地图先行，不堆功能。
  • 花札（HANAFUDA）考据 + 视觉规范 v1：牌面隐喻、术语（添牌 / 撕牌 / 牌阵 / 转生）与视觉一致；牌背从风格样品一路迭代到 v11 手绘卷草角花。
  • 竞品拆解：Jobsync / THRIVE 等欧美流程追踪器的缺失项（测评 DDL、内推、网申窗口、届别）即差异化清单。
  • 上线后按真实摩擦迭代：定版三页重构 → 新手引导 + 术语小词典 → Excel/CSV 批量导入 → 到点提醒 → 校招 / 社招流程预设 → 数据导出 / 导入备份 → AI 三处接入 + 面经采集管道。
